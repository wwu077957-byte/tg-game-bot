# TGVault — Telegram 个人账号管理 Bot（MVP）

本次部署按用户选择，将本程序替换至现有 `@harkNewBot` 服务，因此现有群游戏功能将停止；如需另行部署，建议创建专用 Bot。多位朋友可以使用同一个 Bot，但必须先由部署者把每位使用者的 Telegram 数字用户 ID 加入白名单；数据库操作再按用户 ID 隔离。机器人只接受私聊管理命令。

## 功能与限制

- 手机号验证码登录和 QR 登录；手机号登录先按中文/英文名称或区号搜索并选择国家/地区，再按号码计划校验本地或国际格式。美国与加拿大虽共用 +1，但会额外检查号码归属。
- 按 Telegram 实际返回的验证码类型提示去 Telegram 服务消息、短信、语音电话、闪呼/未接来电或绑定邮箱查找；只有 Telegram 返回 `next_type` 时才提供显式 `/resend`，至少等待 45 秒并遵守服务端 `timeout`/`FLOOD_WAIT`，最多初始一次加四次重发，不自动连发。二维码登录作为备用。
- 账号列表、个人备注、分组、搜索、操作记录、回收站、登录设备和 2FA 状态查看。
- 只有本人正在进行手机号登录、Telegram 报告应用内投递，且本人明确点选号码完全匹配的已保存会话后，才会读取该账号最近 24 小时可识别的 Telegram 登录码；不会自动读取其他账号或跨账号收件箱。显示的码会在约 30 秒后尝试删除。若 Telegram 不允许删除，机器人会提醒手动删除。
- 可选安全提醒：只提醒收到 Telegram 官方服务账号的消息，不转发正文或验证码。
- 验证码和 2FA 密码只在内存中短暂处理；机器人会尝试删除用户发来的输入，不写入数据库或日志。
- 会话、手机号、备注、分组名称和操作记录文本均使用 Fernet 加密后存储。错误验证码每个手机号最多 5 次失败，2FA 密码每个账号最多 3 次失败；两者每次尝试至少间隔 5 秒，达到上限后冷却 5 分钟。发码冷却按用户和号码分别持久化，每号码 45 秒起、15 分钟内最多 5 次请求（一次初始请求加四次显式重发）；Telegram 返回的 FloodWait 会按秒延长冷却。数据库只保存 HMAC 号码标识，不保存冷却表中的明文号码。
- QR 扫码尚未被 Telegram 确认为账号前，Bot 无法知道目标手机号，因此这段期间的 QR 登录/2FA 冷却按用户共享，而不是按目标账号区分；这是避免更换二维码绕过等待的保守限制。

MVP 不提供账号/会话转交、代他人登录、群发或自动发消息、导入/导出会话、读取普通聊天内容、查看/修改 2FA 密码、撤销设备会话或“账号健康分数”。Firebase 短信等需要官方移动端设备证明的通道不能由此 Bot 完成；若 Telegram 未提供可用的下一通道，请在官方客户端继续或使用二维码登录。

## 部署前提

部署者需要准备：

1. 一个 Telegram Bot token；本次替换部署继续使用现有 `@harkNewBot` token。独立部署应创建专用 Bot，不要复用游戏 Bot token。
2. `my.telegram.org` 的 Telegram API ID 和 API hash。它们不是 Bot token。
3. 部署者本人及每位获准朋友的 Telegram **数字用户 ID**。白名单不接受用户名、手机号或空值。
4. Python 3.11+ 环境、稳定运行的主机、持久化且权限受限的数据目录，以及妥善保管的 Fernet 密钥。
5. 备份、系统更新、磁盘加密和密钥管理方案。备份应与运行主机分开保护；数据库之外也要保护 `.env` 和密钥副本。

## 配置白名单

复制 `.env.example` 为 `.env`，在 `ALLOWED_TELEGRAM_USER_IDS` 中填入部署者自己的数字用户 ID，再用逗号加入每一位明确获准的朋友。例如：

```dotenv
ALLOWED_TELEGRAM_USER_IDS=123456789,987654321
```

以上数字只是格式示例。请从可信的 Telegram 用户 ID 查询方式或你已信任的管理记录中确认每个人的数字 ID；不要仅凭用户名推断。每次增加或移除朋友时，部署者编辑该变量并重启机器人。移除后该用户不能继续交互，重启后也不会恢复其后台安全提醒；已有数据库记录不会自动删除。未列入白名单的用户不会获得机器人功能；白名单本身是“哪些人能使用 Bot”的总开关，并不授予他们访问其他用户账号的权限。空白、格式错误或没有任何 ID 时，Bot 会拒绝启动（fail closed）。

## 本地安装与启动

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

在 `.env` 中填写 Bot token、API ID、API hash、白名单，并生成会话/元数据加密密钥：

```bash
python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

然后启动：

```bash
python -m tg_manager.bot
```

`DATABASE_PATH` 应指向持久化的私有磁盘路径。进程用户需要对数据库及目录有写权限；程序会尽力将目录权限设为 `0700`、数据库设为 `0600`。生产环境应使用专用低权限账户和受管进程服务，限制对环境变量、数据库、备份和日志的访问；不要把 `.env`、数据库、Telegram 会话或 API 凭据提交到 Git。

### 现有数据库升级

首次运行这个版本会把旧版数据库中的手机号、备注、分组名和审计文本迁移为密文，并重写 SQLite 页面。升级前应停止旧进程并做一份受保护的备份；旧备份在迁移前可能仍含明文元数据。升级需要原有 `SESSION_ENCRYPTION_KEY`，不能用新密钥替换。确认升级成功后，再按你的保留策略处理旧明文备份。

## 信任边界与数据保护

这是高敏感应用。Telegram 登录会话相当于账号的登录凭据。登录前，Bot 会明确说明：**Bot/服务器运营者能够访问可用会话，并可借此访问该账号允许的 Telegram 功能**；用户必须发送 `/consent` 才能继续。不信任运营者或服务器时，不要使用此 Bot，直接用 Telegram 官方客户端登录更合适。加密是静态存储保护，**不是端到端加密**。

会话和敏感元数据使用同一个 `SESSION_ENCRYPTION_KEY` 加密。运行中的应用必须能读取密钥，因此有主机、进程或密钥访问权的人仍属于可信方。丢失或更换密钥会使已保存会话和加密元数据无法解密；应离线保护并测试密钥备份，不能把密钥和数据库放在同一个可任意读取的位置。

为实现按用户隔离和限流，以下必要的结构化字段仍以明文存在：Telegram 用户 ID、内部账号/分组 ID、账号与分组之间的关联、创建/删除时间、设置状态，以及失败次数和冷却时间。审计动作/详情文本、完整手机号、备注和分组名称均加密；审计记录限制为每位用户最近 500 条。应用读取数据时会先按当前用户 ID 过滤，再解密该用户的数据。数据库加密不能防止恶意或已被攻陷的服务器操作员读取运行进程中的数据。

Bot 与 Telegram 之间的私聊仍受 Telegram 平台和客户端保护方式约束；Bot 私聊不是端到端加密聊天。机器人会尽量删除用户发来的验证码/密码，并在约 30 秒后删除自己显示的检索验证码，但删除能力取决于 Telegram；用户仍应检查并清理聊天记录。验证码或 2FA 密码不要转发给他人。

## 账号所有权与隔离

每个记录都按 Telegram 用户 ID 做数据库级归属检查；没有匹配的所有者 ID 时，读取、更新、删除、恢复或获取会话都会失败。所有获准用户都能和 Bot 交互，但各自只能访问本人添加的账号。朋友必须本人在私聊中完成登录授权。机器人不支持转交会话或替他人登录。

## 命令

`/accounts`、`/add`、`/qr`、`/consent`、`/resend`、`/code`、`/groups`、`/group_create 分组名`、`/move 账号ID 分组名`、`/rename 账号ID 新备注`、`/devices`、`/2fa`、`/search 关键词`、`/notify_on`、`/notify_off`、`/audit`、`/trash`、`/delete 账号ID`、`/restore 账号ID`、`/cancel`、`/help`。`/add` 在明确同意后会提供国家/地区按钮及搜索。只有当本人正在手机号登录且号码匹配时，“获取验证码”或 `/code` 才会显示同号账号按钮；必须由本人明确点选，读取的是本人该会话的 777000，不会自动读取。`/devices` 与 `/2fa` 仍可直接打开只含本人账号的选择器；为兼容旧用法，也可在这些命令后输入本人账号 ID。

当前代码仅为 MVP。本次部署会替换 Bot 功能，但不会自动完成主机隔离、备份方案、数据恢复演练或真实 Telegram 账号验证。
